# Task 1 Report

## Aim and requirements

Repair the fee window using a UI/service/repository design. Java 17, Swing,
`SwingWorker`, validation, safe JDBC patterns, and an in-memory repository are
used.

## Deficiencies

The original design has: one listener with an if-else chain; `==` on action
commands; no validation or `NumberFormatException` handling; SQL
concatenation/injection; database work and `Thread.sleep(3000)` on the EDT;
no user feedback beyond `System.out`; an unhandled Receipt branch that can
fall into clearing logic; leaked connections; no close handling; unchecked
checked exceptions; and a missing comma in the SQL string. The user sees a
frozen window, silent failures, lost input, invalid payments, security risk,
or a crash.

## Structure

```text
FeeWindow --SwingWorker--> FeeService --> PaymentRepository
                                      --> InMemoryPaymentRepository
                                      --> JDBC implementation (production adapter)
```

## Defence

The UI only collects input and displays results. FeeService validates business
rules, while a repository isolates persistence. SwingWorker prevents payment
work from freezing the EDT. Separate listeners make each action readable and
testable. An in-memory repository makes demonstrations deterministic without
requiring MySQL, while the repository boundary permits a PreparedStatement
adapter in production.

## Alternative and complexity

An if-else dispatch chain may compare up to `k` commands: `O(k)` time and
`O(1)` extra listener space. Separate listeners or Swing Actions dispatch in
`O(1)` expected time and use `O(k)` listener objects. Both are linear in the
number of controls, but separate handlers are safer to change.
